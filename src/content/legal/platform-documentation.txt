# Calendar

The Calendar section is where you manage your property’s booking activity, availability rules, blocked dates, and calendar synchronization with external booking platforms.

At the top of this section, you will see three tabs:

Calendar | Availability | Calendar Sync

Each tab handles a different part of your property’s availability management.

Help videos coming soon

## Calendar Tab

The Calendar tab gives you a visual monthly view of what is happening with your property.

From this calendar, you can quickly see bookings, payment activity, owner blocks, imported calendar dates, and cleaning activity.

### Calendar Status Colors

The legend above the calendar identifies the different types of activity:

- Confirmed — confirmed guest reservations
- Pending Review — booking requests waiting for your review
- Pending Payment — approved reservations waiting for payment
- Payment Conflict — a booking with a payment-related issue that may require attention
- Owner Block — dates you have manually blocked for personal use or another reason
- iCal Import — unavailable dates imported from an external booking platform
- Cleaning — scheduled cleaning activity
These colors make it easy to scan the month and understand what is happening without opening each individual item.

### Viewing Calendar Details

Select an item on the calendar to see more information about it.

Depending on the type of item, the details may show information such as:

- Date
- Booking or activity type
- Source
- External booking platform
- Cleaning information
- Other relevant details
For example, selecting an imported calendar event may show the date, the source listing, and the platform it came from.

### Calendar Navigation

Use the arrows beside the month to move backward or forward through the calendar.

Select Today to quickly return to the current month.

The refresh control can be used to refresh the calendar information when needed.

## Availability Tab

The Availability tab controls the rules that determine when and how guests are allowed to book your property.

This area contains settings for:

- Length of stay
- Booking limits
- Owner blocks
After changing availability settings, select Save availability to save your changes.

Help videos coming soon

### Minimum Nights

Minimum nights determines the shortest stay a guest is allowed to book.

For example:

If Minimum Nights is set to:

1 night

a guest may book a stay of one night or longer.

If you change it to:

3 nights

the guest must select a stay of at least three nights.

Use this setting to establish the minimum length of stay you want to accept.

Help videos coming soon

### Maximum Nights

Maximum nights controls the longest stay a guest may request.

If this is set to:

No limit

there is no maximum stay restriction from this setting.

You can use a maximum-night limit if you do not want guests booking unusually long stays.

Help videos coming soon

### Minimum Notice

Minimum notice controls how close to check-in a guest is allowed to make a booking.

For example, if Minimum Notice is set to:

1 day

a guest generally must book at least one day before their requested arrival.

This can help prevent last-minute reservations when you need time to prepare the property.

Help videos coming soon

### Advance Booking

Advance booking determines how far into the future guests are allowed to make reservations.

For example, if this is set to:

6 months

guests can book dates up to six months into the future.

Dates beyond that booking window will not yet be available for new reservations.

This allows you to control how far ahead you want to commit the property.

### Owner Blocks

The Owner Blocks section allows you to make specific dates unavailable to guests.

Use an Owner Block when the property should not be available for booking because of:

- Personal use
- Maintenance
- Private stays
- Repairs
- Other reasons you want to reserve the property
Select:

+ Add block

to create a new blocked period.

Once dates are blocked, guests will not be able to book those dates through the direct-booking website.

Use this feature whenever you need to intentionally remove dates from availability.

## Calendar Sync Tab

The Calendar Sync tab allows your direct-booking website to exchange availability information with external booking platforms.

This helps reduce the risk of double bookings when your property is listed in more than one place.

There are two main parts:

- iCal Export Feed
- Import Calendars
Help videos coming soon

### iCAL EXPORT FEED

The iCal Export Feed provides a calendar URL that compatible external booking platforms can use to import unavailable dates from this system.

This may be used with platforms such as Airbnb, VRBO, Booking.com, or other services that support iCal calendar feeds.

The feed allows external platforms to receive your confirmed booking and blocked-date information so those dates can also be blocked there.

### Copy

Select Copy to copy the iCal feed URL.

You can then paste that URL into the calendar-import area of the external booking platform.

### Preview

Select Preview to view the calendar feed.

### Security

The calendar feed uses a protected token.

Although the feed does not include sensitive guest information such as guest names, email addresses, payment data, or full booking details, the URL should still be shared only with trusted calendar platforms.

### Regenerate Token

Select Regenerate token only when necessary.

> WARNING: Regenerating the token makes the previous calendar URL invalid. If you regenerate it, update the calendar URL on every external platform currently using the old feed.

Do not regenerate the token unless you have a reason to replace the existing calendar-feed URL.

Help videos coming soon

### Import Calendars

The Import Calendars area allows this system to receive unavailable dates from external booking platforms.

This is useful when your property is also listed elsewhere.

For example, you can import a calendar from:

- Airbnb
- VRBO
- Other compatible booking platforms
Imported reservations or blocked dates will appear on your main Calendar as iCal Import activity.

### Add Source

Select:

+ Add Source

to add another external calendar.

You will provide the calendar feed URL supplied by the external booking platform.

### Enable or Disable a Source

Each imported calendar can be enabled or disabled.

If a source is disabled, it will not actively synchronize new calendar information until it is enabled again.

### Manual Sync

The sync control beside an imported calendar can be used when you want to manually request an update from that source.

### Delete a Source

Use the delete control to permanently remove an imported calendar source.

Only delete a source if you no longer want this property to synchronize availability with that external calendar.

### Sync All

Select Sync All to request synchronization for all enabled imported calendars.

Help videos coming soon

> IMPORTANT: Calendar synchronization with external booking platforms is not necessarily instantaneous. Your website can make updated calendar information available immediately, but external platforms determine when they check or refresh imported calendar feeds. Always monitor your calendars when managing the same property across multiple booking platforms.

# Cleaning

The Cleaning page is used to track property turnovers, assign cleaners, and follow each cleaning task from the time it is needed until it is completed. When a guest booking is confirmed, a cleaning task is automatically created for the associated checkout date, helping keep upcoming turnovers organized without requiring manual entry.

At the top of the page, cleaning tasks can be filtered by status:

- All — displays every cleaning task.
- Needed — cleaning is required but has not yet been scheduled or started.
- Scheduled — the cleaning task has been scheduled.
- In Progress — cleaning is currently underway.
- Completed — the cleaning task has been finished.
- Skipped — the cleaning task was intentionally skipped.
These filters make it easy to focus on the cleaning tasks that currently need attention.

## Automatic Cleaning Tasks From Confirmed Bookings

When a booking is confirmed, the system automatically creates a cleaning task for that reservation.

The cleaning task is tied to the guest's checkout date, so the turnover is already placed into the Cleaning Schedule without the property owner having to create it manually.

The owner or manager can then open that cleaning task to:

- assign the cleaner
- update the cleaning status
- add notes or special instructions
- track the task through completion
The + Add task button is mainly for situations where a cleaning task needs to be created manually, such as an extra cleaning, owner-use turnover, maintenance-related cleanup, or another cleaning that is not tied to a confirmed guest booking.

## Adding a Cleaning Task

Click + Add task in the upper-right corner to create a new cleaning task.

The New cleaning task form includes:

Task date
Select the date the cleaning should take place.

Checkout date
Enter the associated guest checkout date. This helps connect the cleaning task with the turnover taking place after a guest's stay.

Assigned to
Enter the name of the cleaner or person responsible for completing the task.

Status
Choose the current status of the cleaning task. A new task can begin as Needed and then be updated as the cleaning progresses.

Available statuses include:

Needed → Scheduled → In Progress → Completed

A task can also be marked Skipped when appropriate.

Notes
Use this area for any additional cleaning instructions or information the cleaner or property manager may need.

Examples might include special turnover instructions, areas requiring extra attention, supply reminders, or other notes related to that cleaning.

When finished, click Save to create the task. Click Cancel to close the form without saving.

## Managing Turnovers

Once cleaning tasks have been created, the Cleaning Schedule becomes the central place for tracking their progress.

Using the status filters, the property owner or manager can quickly see:

- which turnovers still need attention
- which cleanings have been scheduled
- which cleanings are currently being worked on
- which cleanings have been completed
- which tasks were skipped
This helps keep turnovers organized between guest stays and provides a clear record of cleaning activity.

# Maintenance

The Maintenance page is used to track repairs, supply needs, and other property-related tasks that need attention.

At the top of the page, three summary cards give you a quick overview of maintenance activity:

- Open tasks — tasks that still need attention.
- Urgent — tasks marked with urgent priority.
- Total tasks — the total number of maintenance tasks in the system.
You can also filter the task list by status:

- Active — shows tasks that are currently open or in progress.
- All — shows all maintenance tasks.
- Open — tasks that have not yet been started.
- In Progress — tasks currently being worked on.
- Completed — finished tasks.
- Archived — older tasks that have been moved out of the active workflow.
## Adding a Maintenance Task

Click + Add task in the upper-right corner to create a new maintenance task.

The New task form includes:

Title
Enter a short name for the issue or task.

Example:

Fix leaky faucet in bathroom

Description
Add details about the issue, where it is located, and what needs to be done.

Priority
Choose the importance of the task. This helps distinguish routine work from items that need faster attention.

Status
Set the current stage of the maintenance task, such as Open or In Progress.

Category
Choose the type of maintenance task. The screenshot shows General as an available category.

Due date (optional)
Add a due date when the task needs to be completed by a certain day.

When finished, click Save to create the task. Click Cancel to close the form without saving.

## Managing Maintenance Work

The Maintenance page gives the property owner or manager one place to keep track of repairs and property tasks instead of relying on texts, notes, or memory.

As work progresses, tasks can be updated from Open to In Progress and then Completed. Older tasks can be Archived when they no longer need to remain in the active list.

The priority and status filters make it easier to quickly identify what needs attention and what has already been handled.

## Basic Information

The Basic Info tab contains the core information about the property. Much of the information entered here is displayed throughout the live website, so changes should be reviewed carefully before saving.

After making changes, click Save in the upper-right corner.

### Property Details

Title
Enter the main property title used to identify and market the rental on the website.

This should clearly describe the property and can include a short selling point or feature.

Location
Enter the location that should be displayed for the property.

Latitude & Longitude
These coordinates control the exact property location used by the website's map.

Use accurate coordinates so the map is positioned correctly.

### Property Capacity

The following fields describe the property's accommodations:

- Max Guests — maximum number of guests the property can accommodate.
- Bedrooms — total number of bedrooms.
- Beds — total number of beds.
- Bathrooms — total number of bathrooms.
These details are used on the live website to help guests quickly understand the size and capacity of the property.

### Property Description

Use the Description field for the main description of the rental.

This is where you can explain:

- what makes the property unique
- important features and amenities
- nearby attractions or activities
- the type of experience guests can expect
- other useful information about the property

Host Name

Years Hosting

The Host Photo is displayed as part of the property's host information on the live website.

- Replace the current host photo

## Photos

The Photos tab controls the images shown throughout the public property website, including the main property gallery and the organized photo tour.

Photos can be uploaded directly, added by URL, organized into areas, and reordered to control how guests see the property.

### Main Page Photos

The Main Page section controls the primary photos displayed in the main gallery on the public property page.

You can add photos in two ways:

- Upload — upload an image from your device.
- Add URL — add an image using an image URL.
Supported image types include:

- JPG
- PNG
- WebP
Images up to 25 MB can be uploaded.

The first photo in this section is used as the cover image.

> TIP: Place the strongest main property photo first because the first photo becomes the cover image shown to guests.

### Reordering Photos

Photos can be dragged and reordered.

The order shown in the admin determines the order in which the photos appear to guests.

Because the first image is used as the cover image, reordering the photos can also change which image represents the property first on the public website.

### Photo Tour Areas

Below the Main Page gallery are the Photo Tour Areas.

These sections organize property photos by room, area, or feature so guests can browse the property in a more structured way.

Click + Add Area to create another photo-tour section.

Each area can contain:

- its own group of photos
- a custom area name
- features or amenities associated with that area
Areas can also be reordered using the drag handle.

### Bedroom Areas on the Homepage

Bedroom areas in the Photo Tour also supply the bedroom cards displayed in the **Where You’ll Sleep** section on the homepage.

- **Area Title** — the Photo Tour area title is used as the bedroom name shown on the homepage.
- **First Photo** — the first photo in that Photo Tour area is used as the bedroom card image on the homepage.
- **Photo Order** — if the photos are reordered, the new first photo becomes the image displayed on the homepage.
- **Room Name Changes** — if the Photo Tour area title is changed, the bedroom name shown on the homepage changes with it.
- **View Photos** — selecting the bedroom card on the homepage takes the guest directly to that bedroom’s corresponding section in the Photo Tour.

> TIP: For bedroom areas, make sure the title is correct and place the photo you want representing the room first. The homepage uses those Photo Tour settings automatically.

### Managing Photos Within an Area

Each Photo Tour Area has its own photo gallery.

Use Upload or Add URL to add additional images.

The first image within an area is identified as its Cover image for that section.

> TIP: Arrange photos in the order you want guests to view them. The first photo is the cover image for that Photo Tour area.

### Features & Amenities

Each Photo Tour Area can also include Features / Amenities tags.

Use these tags to identify features guests can see or use within that particular area.

You can:

- add a feature
- remove an existing feature
- associate several features with the same area
This helps give guests additional context while browsing the photo tour.

### Managing Photo Tour Areas

Each area includes controls for managing the section.

Depending on the action needed, you can:

- reorder the area
- expand or collapse it
- add or remove photos

## Pricing

The Pricing section controls the property's nightly rates, date-specific pricing, seasonal pricing, minimum-stay rules, taxes, and fees.

There are two tabs:

- Rates — nightly pricing, calendar overrides, seasonal pricing, and minimum-stay controls.
- Fees — additional charges applied to reservations.
The pricing system uses a specific order of precedence so that more specific pricing rules override more general ones.

### Base Settings

The Base settings card contains the property's standard pricing information.

Default nightly rate
This is the fallback nightly price. If no more specific pricing rule applies to a date, the default nightly rate is used.

Tax rate
Enter the percentage of tax that should be applied to applicable bookings.

Displayed price on booking card
Choose how the starting nightly price is presented to guests before they select stay dates.

There are two options:

- Default rate — displays the property's default nightly rate.
- Nightly avg — displays the average of the configured day-of-week rates.
When calculating the nightly average, all seven days of the week are considered. If a particular weekday does not have its own custom rate, the default nightly rate is used for that day when calculating the average.

This displayed amount is primarily an introductory price shown before dates are selected. Once guests choose actual stay dates, the reservation is priced using the rates that apply to those specific dates.

Click Save after changing the Base Settings.

### Nightly Rates by Day of Week

Turn on Customize by day of week when different nightly rates should apply depending on the day of the week.

Separate rates can be configured for:

- Sunday
- Monday
- Tuesday
- Wednesday
- Thursday
- Friday
- Saturday
For example, this allows weekday pricing and weekend pricing to be different.

If a weekday does not have its own custom rate, the system falls back to the Default nightly rate.

If an existing day-of-week rate is cleared, that weekday returns to using the default rate rather than retaining the previous custom amount.

Click Save rates after making changes.

Changes to these general rates do not retroactively change existing reservations, pending booking requests, or dates that already have their own custom date price.

### Pricing Calendar

The Pricing Calendar shows the nightly rate currently applying to each date.

The calendar also provides two important date-specific controls:

Click nightly price to set custom price
Click moon/min to set custom min stay

These controls allow individual dates to override broader pricing or minimum-stay rules.

The legend beneath the calendar identifies:

- Custom date price
- Custom min nights
- Day-of-week / base rate

### Custom Price for a Specific Date

Click the nightly price displayed inside a calendar date to set a custom price for that specific date.

A custom-date editor opens where the nightly price can be entered and saved.

A date-specific price has the highest pricing priority.

### Nightly Price Priority

When determining the nightly price for a selected date, the system uses this order:

1. Custom date price
↓
2. Seasonal pricing
↓
3. Day-of-week rate
↓
4. Default nightly rate

This means a custom price entered directly on a calendar date takes priority over every broader pricing rule.

> IMPORTANT: Date-specific overrides take priority over seasonal, day-of-week, and default pricing settings.

### Editing an Existing Custom Price

Once a custom date price has been saved, it appears in the Custom date prices list.

An existing custom price can be reopened and changed instead of creating another price for the same date.

You can edit it by:

- clicking the saved date/price
- clicking the pencil icon
- clicking that date's nightly price again on the calendar
The existing value is loaded into the editor so it can be changed and saved.

The X removes the custom date price.

There should only be one custom price for a particular date.

### Custom Minimum Stay by Date

Hover over an available calendar date to reveal the moon/min control.

Click it to set a custom minimum stay beginning on that check-in date.

The editor explains:

Set a custom minimum stay starting on this date. Leave blank or set to 0 to remove the override.

Once saved, the calendar displays a small moon indicator showing that the date has its own minimum-night rule.

Click that indicator again to edit the existing minimum stay.

A date-specific minimum stay can be either higher or lower than the broader minimum-stay setting. It is treated as a true override rather than simply taking whichever number is highest.

### Minimum-Stay Priority

Minimum-night rules have their own precedence separate from nightly pricing.

For a guest's check-in date, the system uses:

1. Custom minimum stay for that specific date
↓
2. Seasonal minimum stay
↓
3. Property-wide/default minimum stay

For example, if the normal property minimum is 2 nights and a season requires 4 nights, a guest checking in during that season must stay at least 4 nights.

However, if one check-in date within that season has its own custom 3-night minimum, that date requires 3 nights because the date-specific rule takes priority.

The same rule works in the opposite direction. A date-specific or seasonal minimum can intentionally lower the broader default as well.

These minimum-stay rules are enforced in both the guest booking experience and the checkout process.

> IMPORTANT: Minimum-stay priority is based on the guest’s check-in date: specific date override → seasonal minimum → property default.

### Seasonal Pricing

The Seasonal Pricing section allows rates and minimum-stay requirements to be applied across a date range.

Click + Add preset to create a seasonal pricing period.

A seasonal preset can be used for periods such as:

- holidays
- peak season
- special events
- summer or winter pricing
- slower travel periods
- other date ranges requiring different rates
A seasonal preset can include its own:

- date range
- nightly rate
- minimum-night requirement
- priority
Seasonal presets can also be activated, deactivated, edited, or deleted.

### Overlapping Seasonal Presets

If more than one active seasonal preset applies to the same date, the preset with the higher priority is used.

The winning seasonal preset controls both its seasonal nightly rate and its seasonal minimum-stay rule.

This keeps overlapping seasonal rules predictable rather than combining multiple presets.

### How All the Pricing Layers Work Together

The easiest way to understand this section is to think of pricing as layers.

### Nightly Price

Specific date → Season → Day of week → Default

The system always uses the most specific applicable price.

### Minimum Stay

Specific check-in date → Season → Property default

The system always uses the most specific applicable minimum-stay rule.

Pricing and minimum-stay rules are related, but they are resolved independently. For example, a date may use a seasonal nightly price while also having its own custom minimum-stay override.

### What Guests Are Charged

Once the guest selects actual reservation dates, the system calculates the stay using the applicable nightly rate for those dates.

That means seasonal rates and custom date prices are reflected in the actual reservation quote and checkout—not merely displayed in the admin calendar.

The applicable fees and taxes are then added to produce the final booking total.

# Payments

## Payment Mode

The Payment Mode controls both **when the guest pays** and **whether the booking requires administrator approval before payment**.

The four available modes are:

- Manual Test
- Stripe Test
- Manual Live
- Stripe Live

The easiest way to understand the difference is:

**Manual modes = Request first → Admin reviews → Payment after approval**

**Stripe modes = Available dates → Guest goes directly to checkout**

> IMPORTANT: "Manual" does not mean the booking or payment has to be handled outside the platform. It means the guest's request must be reviewed by the administrator before the guest proceeds with payment.

### Manual Test

Manual Test is used to test the **request-and-approval booking workflow** without processing a real payment.

When a guest selects available dates and submits the booking:

1. The guest sends a booking request instead of going directly to Stripe Checkout.
2. The requested dates are held while the booking is waiting for administrator review.
3. The administrator reviews the booking request.
4. The administrator can approve or decline the request.
5. If the request is approved, the booking moves forward to the payment step.
6. The guest receives the applicable automated email with a payment link to complete payment.
7. The payment is completed using the test payment workflow, so no real money is charged.

Use Manual Test when you want to test the complete administrator-review process before allowing the guest to complete payment.

> TIP: Manual Test is useful for properties where the owner wants to review the guest, dates, occupancy, pets, special requests, or other booking details before allowing payment.

### Stripe Test

Stripe Test is used to test the **immediate checkout workflow** without charging real money.

When a guest selects dates:

1. The platform checks whether the requested dates are available.
2. If the dates are available and the booking meets the applicable rules, the guest can continue directly to Stripe Checkout.
3. The guest does not wait for administrator approval before reaching the payment page.
4. Stripe Test credentials are used, so the checkout behaves like a real payment without charging a real card.
5. After the test payment succeeds, the platform processes the booking through the normal online-payment workflow.

Stripe Test can be used to verify:

- checkout
- successful payments
- failed payments
- booking confirmation
- webhook processing
- payment-related emails
- refunds and other supported payment workflows

Use Stripe Test when you want to test the guest experience of selecting available dates and proceeding directly to payment.

> TIP: Stripe Test is the best mode for testing the complete online checkout experience before switching the property to Stripe Live.

### Manual Live

Manual Live uses the same **request-and-approval workflow** as Manual Test, but it is intended for real guest bookings and real payments.

When a guest submits a booking:

1. The guest sends a booking request instead of going directly to checkout.
2. The requested dates are held while the administrator reviews the request.
3. The administrator approves or declines the request.
4. If the request is declined, the booking does not proceed to payment.
5. If the request is approved, the guest receives the applicable automated email with a payment link.
6. The guest can then complete payment using the live payment workflow.
7. A completed live Stripe payment is a real charge.

Use Manual Live when the property owner wants to review each booking request before allowing the guest to pay.

> IMPORTANT: Manual Live gives the administrator control over whether a booking request is accepted before the guest is allowed to complete payment.

### Stripe Live

Stripe Live is the **immediate live checkout workflow**.

When a guest selects dates:

1. The platform checks whether the dates are available.
2. The platform applies the property's booking, pricing, minimum-stay, guest-count, and other applicable rules.
3. If the stay qualifies, the guest can proceed directly to Stripe Checkout.
4. Administrator approval is not required before checkout.
5. The guest enters a real payment method.
6. Stripe processes a real charge.
7. The booking and payment records are updated through the live payment workflow.

Use Stripe Live when guests should be able to book available dates and pay immediately without waiting for the administrator to manually approve the request first.

> WARNING: Stripe Live processes real payment methods and real charges. Only enable Stripe Live after the property, pricing, availability, emails, Stripe credentials, and webhook configuration have been fully tested.

Before switching to Stripe Live, confirm that:

- the live secret key is configured
- the live publishable key is configured
- the live webhook signing secret is configured
- the live webhook destination is active in Stripe
- the website is ready for real guests

The Test credentials can remain saved. There is no need to delete them when switching to Stripe Live.

This makes it easy to switch back to Stripe Test later if additional testing is required.

### Manual vs. Stripe at a Glance

**Manual Test / Manual Live**

Guest selects dates → Booking request submitted → Dates held → Administrator reviews → Approve or decline → Approved guest receives payment link → Guest completes payment

**Stripe Test / Stripe Live**

Guest selects dates → Availability and booking rules are checked → Guest proceeds directly to Stripe Checkout → Payment is completed → Booking continues through the payment workflow

The difference between **Test** and **Live** is whether real money is processed.

- **Test** modes are for testing and do not process real charges.
- **Live** modes are for actual guest bookings and process real payments.

## Webhook Endpoint

The Webhook Endpoint section displays the URL that Stripe must send payment events to.

Use the copy button to copy the endpoint exactly as shown.

The same application webhook URL can be used when configuring Stripe, but test and live webhook destinations have separate signing secrets.

In Stripe, create the webhook destination under:

Developers → Webhooks

Configure the endpoint to listen for the payment events required by the platform, including:

- checkout.session.completed
- checkout.session.expired
- payment_intent.payment_failed
- charge.refunded
These events support the major payment workflows.

### checkout.session.completed

Used when a Stripe Checkout payment completes successfully.

This allows the platform to record the successful payment and continue the booking workflow.

### checkout.session.expired

Used when a Stripe Checkout session expires before payment is completed.

This allows expired pending-payment bookings or holds to be handled correctly.

### payment_intent.payment_failed

Used when Stripe reports that a payment attempt failed.

### charge.refunded

Used to synchronize Stripe refund information with the booking after a full or partial refund.

## Test and Live Webhooks

Stripe Test and Stripe Live should each have their own webhook configuration.

Even when both destinations use the same endpoint URL, they have different:

- Stripe environments
- webhook signing secrets
- event deliveries
The test webhook signing secret must be stored in the Test field.

The live webhook signing secret must be stored in the Live field.

Do not interchange them.

## Checkout Settings

### Site URL

The Site URL is the public website address used as the base for Stripe Checkout return URLs.

The platform uses this address when creating Stripe success and cancellation URLs.

For a live property, make sure this contains the correct public website domain.

### Checkout Expiration

The Checkout Expiration setting controls how long a Stripe Checkout session remains available before it expires.

The value is entered in minutes.

The supported range is:

30–1440 minutes

The default is typically 30 minutes.

A shorter expiration helps prevent unpaid checkout sessions from holding reservation dates for too long.

### Pending Payment Cleanup

Expired pending-payment holds are cleaned up automatically.

The system checks for expired pending-payment bookings approximately every 5 minutes.

This helps release dates when a guest begins checkout but never completes payment.

## Switching Between Test and Live

The recommended workflow for a new property is:

1. Configure the Stripe Test credentials.
2. Configure the test webhook.
3. Select Stripe Test.
4. Complete the full booking and payment workflow using Stripe test cards.
5. Confirm bookings, payment records, notifications, and refunds work as expected.
6. Configure the Stripe Live credentials.
7. Configure the live webhook and live signing secret.
8. Leave the site in Stripe Test while the property is still being prepared.
9. When the property is ready for real bookings, select Stripe Live and click Save Settings.
10. Refresh the page and confirm the status shows Stripe Live — ready.
Once Stripe Live is selected, real customer payment methods will result in real charges.

## Security

Stripe secret keys and webhook signing secrets are sensitive credentials.

The platform protects these values by storing them in the Secured Vault rather than as plain-text payment settings.

Security protections include:

- secret keys are encrypted
- webhook secrets are encrypted
- secret values are not returned in normal API responses
- only masked previews are displayed after saving
- publishable keys can be stored normally because they are not secret
- the Payments settings page is restricted to authorized administrators
> WARNING: Never include full sk_test_, sk_live_, or whsec_ values in screenshots, documentation, support messages, or public files.

Publishable keys beginning with pk_test_ or pk_live_ are designed to be publicly usable.
