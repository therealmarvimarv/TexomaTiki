## 1. Executive Summary

This is a **single-property vacation rental management application** branded as "Tiki Cottage." It provides a complete guest-facing booking website and a full-featured administrator dashboard for managing bookings, payments, calendar, pricing, content, emails, cleaning, and maintenance.

- **Primary purpose**: End-to-end vacation rental management - guest booking, payment, calendar sync, automated emails, and property operations.
- **Public guest experience**: A polished listing page with photo gallery, photo tour, amenities, host info, neighborhood highlights, reviews, FAQs, pricing, availability, and booking/inquiry flows.
- **Administrator experience**: A comprehensive dashboard covering calendar, bookings, cleaning, maintenance, property content, pricing, fees, payments, email automation, calendar sync, photos, and account/branding settings.
- **Major external integrations**: Stripe (test and live), SMTP/Resend email, external iCal calendar platforms (Airbnb/VRBO/Booking.com), and a SaaS platform management layer (Netlify/Bolt Database provisioning for multi-client deployments).
- **Overall architecture**: React SPA frontend talking directly to Bolt Database (Postgres + Auth + Storage), with server-side logic in Bolt Database Edge Functions (Deno) and scheduled pg_cron jobs. No traditional backend server is required for the property application itself (a legacy Express/Prisma backend exists in source but is not part of the active deployment).

## 6. Booking System

**Complete booking lifecycle:**

1. **Guest date selection**: Date range picker with availability checking against `public_availability` view (blocked_dates, owner_blocks, confirmed bookings, active pending_payment)
2. **Availability checks**: Validates against blocked_dates, owner_blocks, and overlapping bookings (confirmed + active pending_payment with non-expired payment_expires_at)
3. **Occupancy rules**: Max guests enforcement, adults/children/infants/pets breakdown
4. **Booking request** (manual mode): `create-booking-request` edge function creates booking with `pending_review` status, sends notification emails
5. **Booking checkout** (Stripe mode): `create-checkout-session` edge function creates Stripe Checkout session, sets booking to `pending_payment` with payment_expires_at
6. **Approval**: Admin approves pending_review booking -> if Stripe configured, creates checkout session for guest (pending_payment); if manual, confirms directly (blocks dates, creates cleaning task)
7. **Decline**: Admin declines pending_review booking -> `declined` status, notification sent
8. **Confirmation**: Via Stripe webhook (checkout.session.completed) or manual admin confirm
9. **Cancellation**: Admin cancels confirmed booking -> `cancelled` status, dates released (blocked_dates rows deleted), notification sent
10. **Payment expiration**: Pending_payment bookings expire after configurable timeout (default 30 min), cleaned up by cron job every 5 minutes
11. **Payment failure/conflict**: Amount mismatch or date conflict after payment -> `payment_conflict` status
12. **Refunds**: Full or partial via Stripe (admin-booking-action), cumulative refund tracking, `refunded` or `partially_refunded` payment status. **Refunds do NOT change `booking.status` and do NOT release dates.** Only cancellation releases dates. Refunds update `refunded_amount`, `refunded_at`, and `payment_status` only.
13. **Archiving**: Auto-archive cron at 3:30 AM daily for old bookings; manual archive from booking detail
14. **Internal notes**: `booking_internal_notes` table for admin notes per booking
15. **Payment notes**: Stored on booking record, visible in booking detail
16. **Cleaning task creation**: Auto-created on booking confirmation (checkout date), manually creatable

**Booking statuses**: `pending_review`, `pending_payment`, `confirmed`, `declined`, `expired`, `cancelled`, `payment_failed`, `payment_conflict`, `refunded`

**Payment statuses**: `paid`, `pending`, `unpaid`, `partially_paid`, `expired`, `failed`, `refunded`, `partially_refunded`

**Manual Test vs. Stripe Test vs. Manual Live vs. Stripe Live:**

| Mode | Guest Flow | Payment | Date Blocking |
| --- | --- | --- | --- |
| `test_manual`                      | Submit request -> admin approves -> confirmed                     | No online payment   | On approval (manual confirm) |
| `test_stripe`                      | Submit request -> Stripe Checkout (test keys) -> webhook confirms | Stripe test charges | On webhook confirmation      |
| `live_manual`                      | Same as test_manual                                             | No online payment   | On approval                  |
| `live_stripe`                      | Submit request -> Stripe Checkout (live keys) -> webhook confirms | Real Stripe charges | On webhook confirmation      |

## 7. Pricing Engine

**Nightly rate precedence (highest to lowest):**

1. **Date-specific price override** (`date_price_overrides`): Exact date match wins
2. **Seasonal pricing preset** (`seasonal_pricing_presets`): Highest priority among active presets matching date range
3. **Day-of-week rate** (`day_of_week_rates`): Matches the day of week (0=Sunday)
4. **Base nightly rate** (`properties.base_price`): Fallback

**Minimum-night precedence (highest to lowest):**

1. **Date availability override** (`date_availability_overrides.min_nights`): Exact check-in date match
2. **Seasonal pricing preset** (`seasonal_pricing_presets.min_nights`): Highest priority preset matching check-in date
3. **Property default** (`properties.min_nights`)

**Fee calculation:**

- **Cleaning fee**: A standard `per_stay` (or `per_night`) fee. It is **never** skipped based on pets. It is always included in the quote when enabled and the amount is greater than zero.
- **Pet fee**: A standard `per_stay` (or `per_night`) fee. It is skipped (amount set to 0, filtered out) **only** when the guest selects 0 pets. The skip condition is: `fee.is_standard && fee.name === 'Pets' && pets === 0`. No other fee is affected by the pet count.
- **Additional guest fee**: `per_guest_per_stay` or `per_guest_per_night`, applies after `applies_after_guests` threshold (default 3). Only charged when guest count exceeds the threshold.
- **Custom fees**: Any of `per_stay`, `per_night`, `per_guest_per_stay`, `per_guest_per_night`. Not subject to the pet-skip logic.
- **apply_to_guest_quote**: Fees with this flag set to `false` are excluded from guest-facing quotes entirely.
- **Zero-amount filtering**: All fee lines with `amount <= 0` are filtered out of the final quote.
- **Tax**: Calculated as `(subtotal + feesTotal) * tax_rate`

**Quote calculation**: Per-night sum using `resolveNightlyRate()` for each night, plus applicable fees, plus tax. Consistent between client-side (`src/lib/pricing.ts`) and server-side (`create-checkout-session`, `create-booking-request` edge functions).

## 8. Payments & Stripe

**Four payment modes**: `test_manual`, `test_stripe`, `live_manual`, `live_stripe`

**Credential management:**

- Separate test and live Stripe secret keys, webhook secrets, and publishable keys
- All secrets stored in Bolt Database Vault (never in env vars except as fallback)
- `payment_settings` table stores: payment_mode, site_url, checkout_expires_minutes, publishable keys (non-secret)
- Vault RPCs: `payment_settings_get_secret`, `payment_settings_secret_preview`, `payment_settings_delete_secret`

**Checkout session creation:**

- `create-checkout-session` (public, for guest-initiated checkout): Creates Stripe session, sets booking to `pending_payment`
- `create-checkout-session-for-booking` (admin/authenticated): Creates checkout session for an existing pending_review booking (used during admin approval)

**Payment expiration:**

- `payment_expires_at` set on booking at checkout creation (default 30 min, configurable)
- Cron job `cleanup-expired-pending-payments` runs every 5 minutes, expires stale pending_payment bookings

**Successful payment processing** (stripe-webhook):

1. Verifies Stripe signature (tries test secret, then live secret)
2. Enforces livemode consistency (test secret must match `livemode=false`, live must match `true`)
3. Idempotency via `payment_events` table (unique `stripe_event_id`)
4. Guards: booking must still be `pending_payment`/`pending`; amount must match; re-check date conflicts
5. On success: blocks dates, creates cleaning task, sets `confirmed`, sends notifications
6. On amount mismatch: `payment_conflict`
7. On date conflict: `payment_conflict` (payment received but dates unavailable)

**Refunds:**

- Full refund: Sets `payment_status` to `refunded`, updates `refunded_amount` and `refunded_at`. Does **not** change `booking.status`. Does **not** release dates.
- Partial refund: Updates `refunded_amount` (cumulative), sets `payment_status` to `partially_refunded`. Does **not** change `booking.status`.
- **Stripe environment selection for refunds**: The refund secret key is selected based on the **original Stripe transaction's livemode** as recorded in `payment_events`, NOT the current `payment_mode`. This ensures refunds are always processed against the same Stripe environment that received the original payment, even if the admin has since switched modes.
- Refund email automation triggered (`booking_refunded` trigger type, admin + guest)

**Stripe webhook events handled by the current implementation:**

1. `checkout.session.completed` - payment success (confirms booking, blocks dates, creates cleaning task, sends notifications)
2. `checkout.session.expired` - checkout session expired without payment (marks booking as expired)
3. `payment_intent.payment_failed` - payment failed (marks booking as `payment_failed`)
4. `charge.refunded` - refund processed externally (records event, updates refund tracking if applicable)

- Admin-only edge function (`ical-import`) with JWT verification

- Supports Airbnb, VRBO, Booking.com, Other platforms
- Manual sync (per-source or Sync All), enable/disable sources
- No automatic scheduled import (manual trigger only)

**Photo upload optimization** (in `PhotosEditor.tsx`):

- **Source-size limit**: 25MB (`MAX_SIZE = 25 * 1024 * 1024`)
- **Allowed types**: JPEG, PNG, WebP
- **Max dimension**: 3000px on longest side (`MAX_DIMENSION = 3000`)
- **No upscaling**: Images smaller than 3000px are never enlarged; scale factor remains 1
- **JPEG quality**: 0.85
- **WebP quality**: 0.85
- **PNG handling**: PNG is preserved as PNG (no quality parameter, lossless)
- **Orientation**: EXIF orientation respected via `createImageBitmap(file, { imageOrientation: 'from-image' })`
- **Sequential uploads**: Files processed sequentially in a `for...of` loop (not parallel)
- **Cleanup**: `bitmap.close()` and `URL.revokeObjectURL()` in `finally` block to prevent memory leaks
- **Cover photo**: First photo in each section (sort_order) is labeled "Cover" in the editor UI

**Storage buckets**: `property-photos` (property photos), `branding` (logo, favicon, host photo)

## 15. Authentication, Authorization & Security

**Authentication provider**: Bolt Database Auth (email/password)

**Login**: `/admin/login` - email/password, creates JWT session
**Password reset**: `/admin/reset-password` - Bolt Database Auth reset flow
**Public registration**: Not supported - admin accounts are pre-provisioned

**Admin authorization - verified RLS behavior:**

- `admin_users` table: RLS enabled. The **only** policy is `select_own_admin_users` (SELECT where `auth.uid() = user_id`). There are **no INSERT, UPDATE, or DELETE policies** on this table. This means:
  - Authenticated users can SELECT only their own row
  - No user (including authenticated admins) can insert, update, or delete admin users through the client API
  - New admin users must be provisioned via SQL/migration directly - this is a deliberate security hardening measure
- `account_settings` table: RLS enabled. Anon can SELECT public branding columns only (`anon_select_public_branding`). Authenticated users have full CRUD gated by `is_admin_user()` check on all write operations and SELECT.
- Most public content tables (properties, amenities, highlights, reviews, FAQs, etc.): anon SELECT for public display; administrative writes are governed by the table's RLS policies and the `admin_users` allowlist where `is_admin_user()` is used.
- `bookings`: no direct public access; booking creation happens through edge functions with server-side validation, while admin-side access is protected by authentication/RLS and the project's admin authorization model.
- `blocked_dates`: authenticated SELECT only (public reads via `public_availability` view)
- `payment_settings`, `email_settings`: admin-facing configuration is protected by authentication/RLS; secret values are kept in Vault and accessed through controlled RPC/Edge Function paths rather than normal table columns.
- `admin_users` allowlist enforced via `is_admin_user()` database function, called by RLS policies on protected tables

**Edge Function authorization:**

- Public (no JWT): `create-booking-request`, `create-checkout-session`, `stripe-webhook`, `payment-config-public`, `booking-lookup`, `ical-export`, `send-notifications`, `send-automated-emails`
- JWT required: `admin-booking-action`, `email-settings-status`, `email-settings-update`, `payment-settings-status`, `payment-settings-update`, `create-checkout-session-for-booking`, `ical-export-token`, `ical-import`, `email-templates-update`, `email-templates-reset`
- `send-automated-emails`: Accepts both service-role key (cron) and user JWT (admin test)

**Security-hardening items (implemented, verified):**

- `admin_users` table has no client-write policies - admin provisioning is SQL-only
- `account_settings` anon access restricted to branding columns only
- `public_availability` view secured with SELECT-only grants
- Stripe webhook signature verification with livemode consistency check
- iCal import SSRF protection (private IP/localhost/metadata blocking)
- iCal export token-gated with no PII in feed
- Payment amount verification on webhook
- Date conflict re-checking on webhook and admin actions
- Idempotency via `payment_events` unique constraint
- Refund Stripe environment selected from original transaction livemode, not current mode

### 30.7 Automatic iCal Import Scheduling - Live Production Implementation

The V1.0.0 baseline states in Sections 10, 25, and 26 that iCal import is manual-only. That is no longer true for this live production client.

V1.0.1 adds automatic external iCal import synchronization every 15 minutes while preserving all manual administrator synchronization controls.

The live production implementation uses:

- `public.run_ical_import()` as the scheduled database function
- `pg_cron` for the recurring schedule
- `pg_net` for the Edge Function HTTP request
- Bolt Database Vault for scheduler authentication material
- the Vault-managed `edge_service_role_key`
- `public.verify_ical_scheduler_token()` to validate the scheduled path securely
- the existing `ical-import` Edge Function

Automatic import schedule:

```text
Every 15 minutes
```

Manual behavior remains available and unchanged:

- per-source Sync
- Sync All
- source enable/disable
- existing iCal parsing
- existing blocked-date synchronization
- iCal export
- signed-in administrator authentication for the manual Sync All path

A real scheduled production execution was verified to return HTTP 200 and synchronize both configured Airbnb and Vrbo feeds with no synchronization errors.

External reservation visibility can still depend on how quickly Airbnb, Vrbo, Booking.com, or another external platform publishes changes to its iCal feed.
